## 18. 缺省实施约定登记（全部 DEFAULT，未经逐题确认）

根据用户在 RCF-088 后授权的统一策略，以下是为了使架构文档可落地而补充的**缺省设计约定**。它们使用 DFL 编号，与用户显式确认的 RCF 编号分离。任何 DFL 均可被后续显式修订，不能声称是用户逐项选择。

| ID | 来源 | 缺省实施约定 | 边界与验证 |
|---|---|---|---|
| DFL-001 | DEFAULT | 采用「接口契约优先、最小实现跟进」的实现顺序 | 不把未来组件的复杂占位实现带进 MVP |
| DFL-002 | DEFAULT | 权威命令需要稳定操作标识和来源 Session 关联 | 与具体网络序列化格式无关 |
| DFL-003 | DEFAULT | 运行中注册表冻结，重载可替换资源/有限配置但不动态改变世界 Schema | 规则代码热替换留到后期 |
| DFL-004 | DEFAULT | 世界数据在逻辑对象边界有版本号及明确的已写回/已同步状态 | 不把一个全局 Dirty Flag 当全部消费者进度 |
| DFL-005 | DEFAULT | 后台任务读不可变快照、结果附源版本、经安全同步点提交 | 具体 Arc/CoW/复制策略不预先绑定 |
| DFL-006 | DEFAULT | 对于尚无精细依赖图的消费者，可保守失效并重建派生数据 | 正确性优先于缓存命中率 |
| DFL-007 | DEFAULT | 新模组能力同时声明语义版本、所需权限及可用阶段 | 不默认第三方代码可安全执行 |
| DFL-008 | DEFAULT | 能力解析不成功时优先生成结构化诊断并拒绝世界激活 | 不静默更换核心规则版本 |
| DFL-009 | DEFAULT | 跨维度能力以显式关系白名单申请，默认不隐含物理/投射/声音传播 | 仅远端渲染不自动启用模拟 Tick |
| DFL-010 | DEFAULT | 原版兼容测试采用「规格 ID → 证据 → 用例 → 结果」追踪链 | 不以主观相似替代差分验证 |
| DFL-011 | DEFAULT | 模组引用的持久标识采用命名空间 + 类型/模式版本，运行时 ID 非持久 | 数据迁移必须显式记录 |
| DFL-012 | DEFAULT | 权威日志与客户端诊断采用明确事件分类和敏感字段脱敏 | 追踪不得改变模拟语义 |
| DFL-013 | DEFAULT | 用户配置、规则预设和模组配置使用 Schema 验证、来源跟踪与明确优先级 | 运行时修改的可逆性不得夸大 |
| DFL-014 | DEFAULT | MVP 平台测试以 Linux/Vulkan 为发布阻断门槛，其余平台预研不阻断 MVP | 具体发行平台版本矩阵仍 TBD |
| DFL-015 | DEFAULT | 保存与恢复先建立可靠的完整检查点，再增量与在线备份 | 恢复默认到独立位置，不覆盖原世界 |
| DFL-016 | DEFAULT | 客户端图形质量分级不修改服务器权威光照、碰撞和战斗判定 | 远端多视图性能可降级显示而非改变规则 |
| DFL-017 | DEFAULT | 初始模组、世界生成和规则测试使用可复现配置集与固定种子 | 不指定未经实测的性能承诺 |
| DFL-018 | DEFAULT | 高成本特性进入后续阶段前，需要明确能力边界、依赖、回退和验收场景 | 不能借「扩展性」无限扩张 MVP |
| DFL-019 | DEFAULT | 版本号和兼容性声明分开：引擎版本不直接等于 Java/Bedrock 行为版本 | 一个 Preset 需列出受验证的能力集合 |
| DFL-020 | DEFAULT | 全部架构记录统一保留 EXPLICIT/DEFAULT/TBD 标记及变更历史 | 任何自动推定决策不能回填为用户显式选择 |

**实施解释：** DFL 是基于既有已确认原则推导出的开发约定，而非新增的强制技术栈选择。例如「缓存使用版本校验」有上位 RCF 硬约束，但「从哪种源版本字段实现」仍由具体设计和测试决定。

### 19.1 决策来源

- P1 启动时，用户确认虚拟工作区、ECS 策略及 Vulkan 绑定。首个 P2 里程碑确认可并行推进无窗口工作、实现权威移动与方块交互，并采用平坦分层地形。参见 [P1 决策](p1-decisions.md)与 [P2 首个里程碑](p2-milestone-1.md)。
- 2026-11-19 的 P1–P3 决策轮，用户依次确认 008A、009B、010A、011A、006B、007B、013B、014A、015A、017A、018A、024B、002B、003A、022B、023A。014A 同时适用于 UI A 和音频 A。
- P2 库存与存档开发时，用户确认有限堆叠及方块与库存原子提交，并选定平坦维度默认 `-64 ≤ y < 256`。
- P2 图形开发时，用户确认高对比纯色原型、同轮接入第一人称窗口与键鼠和快捷栏，并提供 Gentoo / KWin Wayland 主验收机配置。
- P2 操作界面开发时，用户确认单人 Esc 菜单冻结权威 Tick，首版操作设置持久化鼠标灵敏度与 Y 轴反转。
- 用户确认此前桌面键鼠验收通过，并反馈恢复后需要再次点击。随后确认首版交互反馈采用选中描边和准星短闪，首批音效覆盖放置、破坏与脚步。
- P2 音频开发时，用户确认首版居中播放、持久化主音量和静音，以及进入暂停时停止当前音效。
- 启动 P3 时，用户选定现有 Gentoo 笔记本为首轮性能参考机，并决定从首轮直接接入专用 GPU Runner 作为首帧验收门槛。Runner 尚未注册，用户确认采用 `rustcraft-gpu` 标签。
- P3 首轮性能采样前，用户选定区块生命周期与首次生成为主要负载，采用半径 1、2、4 比较 Tick 耗时和内存。
- Gentoo 无窗口采样完成后，用户选定 Intel Raptor Lake-S 核显作为首轮客户端帧时间基线设备。
- 客户端基准开发时，用户确认使用 1920×1080 像素分辨率，并采用原地匀速转向场景。
- Intel 核显首轮采样后，用户确认首版游戏默认视距采用半径 2，半径 4 可作为高视距档。
- 接入运行时视距时，用户确认采用暂停菜单持久设置，恢复后生效。跨区块或提高视距时采用近处优先的分批加载。
- 接入 F3 调试 HUD 时，用户确认显示帧间隔、待建网格数与准星命中目标。首版 F3+G 显示玩家当前区块的边界。
- 用户确认 F3 HUD 与 F3+G 区块边界的桌面实机验收通过，并选定 1920×1080 像素下沿直线跨过三个新区块再原路返回，作为首轮真实窗口流送采样路线。
- Gentoo 首轮窗口采样后，用户选定跨区块后视野补齐耗时作为首个性能门槛。呈现间隔继续采集，具体阈值根据重复采样确定。
- Gentoo 六次窗口复测后，用户确认半径 2 的补齐上限为 135 ms，半径 4 为 235 ms。
- 用户选定世界生成作为 P3 原生预设首个独立版本化能力，已有世界继续使用创建时的平坦生成语义。
- 用户要求加入双击跳跃触发的飞行及下降触地恢复行走，并连续提供 1–16 视距。扩展后测试节点为 1、4、8、12、16。
- 用户确认此前的飞行与视距测试通过，并要求再次双击空格可取消飞行。下一项权威规则选择锁定现有 Tick 调度顺序。
- 用户选定 P3 的只读存档校验首版检查 `CURRENT` 指向的检查点，用于启动、备份或恢复前验证。
- 用户确认客户端和独立服务端统一提供 `--open-world DIR`，严格打开已有存档。
- 用户选定玩家移动为下一项版本化权威规则，锁定跳跃、飞行、重力和碰撞。已有世界继续使用版本 1 的移动语义（[§10.2](simulation.md#section-10-2)）。
- 用户确认全高区块调试线。当前区块逐层使用绿色横线，16 格区段线保留原青蓝色，当前区块和外围已渲染区块的角线改为黄色（[§9.5](client.md#section-9-5)）。
- 用户将黄色角线范围改为以玩家所在区块为中心的 3×3 区块，并将当前区块的横线范围缩至玩家所在子区块附近（[§9.5](client.md#section-9-5)）。
- 用户选定方块与库存作为下一项版本化权威规则。旧存档沿用版本 1 的放置、破坏、槽位操作与原子提交（[§10.2–10.3](simulation.md#section-10-2)）。
- 用户选定世界、维度、区块和系统的确定性种子派生，保留平坦地形原有生成语义（[§4.4](simulation.md#section-4-4)）。
- 用户选定存档恢复重放，用相同输入比较连续运行与磁盘恢复后的玩家移动、库存、方块和区块状态（[§15.1](development.md#section-15-1)）。
- 用户选定候选清单作为指定代恢复的辅助操作，显示代号、Tick 和当前标记（[§13.7](persistence.md#section-13-7)）。
- 用户选定可独立推进并保存的原生系统随机流，以保存恢复后序列连续为验收条件（[§4.4](simulation.md#section-4-4)）。
- 用户选定延迟任务首版按到期 Tick 稳定排序、支持显式取消和存档恢复，并以到期事件验收（[§4.5](simulation.md#section-4-5)）。
- 用户选定 [P3 验收清单](p3-acceptance.md)作为本地门槛、GitHub CI、GPU Runner 和 Gentoo 实机剩余证据的归档入口。
- 2026-11-19 用户确认已配置专用 GPU Runner。本机 `Gentoo-Impact` 的注册配置及等待作业日志已核对，验收证据见 [P3 验收清单](p3-acceptance.md)。
- 用户随后延期远端 GPU 首帧验收，计划另找云服务器。当前以本地开发和验收为准（TBD-024）。
- 用户确认同轮接入定时方块替换、定时区块停用及本地服务端任务诊断，行为与验收命令见 [§4.5](simulation.md#section-4-5)。
- 用户确认 P3 加入已有存档的离线任务排队与取消，并用保存恢复重放验收。实机门槛为 Gentoo Intel 核显、Wayland、1920×1080 下的五档窗口流送。同机补测 NVIDIA 独显，X11 暂不支持。用户指定 Java Edition 1.20.1 为首个 P4 兼容目标，并授权从现有 Prism Launcher 安装提取 Git 忽略的本地参考资源。
- 用户确认 P4 同轮推进超平坦、生存交互和红石差分，红石用例包含拉杆、红石粉、红石灯、中继器及活塞。逐 Tick 调试支持单步推进及 256 Tick 只读回看。使用本地最小资源包和本地命令行验收。参见 [P4 兼容验证](p4-compatibility.md)。
