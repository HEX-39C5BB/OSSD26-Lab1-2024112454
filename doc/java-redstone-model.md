## 规则范围和身份

**EXPLICIT** 参考规则集为 `java/1.20.1`。版本身份须记录在追踪、差分用例和可重放世界中。运行时通过已解析的行为规则确定事件、方块状态和时序。`rustcraft:java_1_20_1_flat@1` 继续承载已有超平坦存档。新建时选择 `java-1.20.1-reference` 使用 `rustcraft:java_1_20_1_flat@2`，采用时序版本 2 和 Java 内容包 0.2.0。新建时选择 `java-1.20.1-reference-v3` 使用 `rustcraft:java_1_20_1_flat@3`，沿用时序版本 2 和内容包 0.2.0，并按原版重开实验区分临时事件和持久数据。旧入口及存档继续绑定原版本，不自动迁移。具体能力以矩阵中的验证范围为准。Java 其他版本、Redstone Experiments、Bedrock、Strict 各自解析自己的规则身份和实现版本。[RCF-023、024、033](rcf-decisions.md) · [规则组合](simulation.md#section-5)

本文中的“映射支持”表示在 1.20.1 版本映射中能区分接口或状态。“原版实测”限定在记录的装置、输入阶段和观察面。其余精确规则标为 **TBD**，由实验填补。

## 时间和执行阶段

| 名称 | 参考契约 |
|---|---|
| GT（Game Tick） | 唯一逻辑时间。正常目标 20 GT/s，名义 50 ms/GT。权威 GT 序号与实际赶进度消耗的墙钟时间分离。一次 GT 可记录多次、有序的更新。 |
| RT（Redstone Tick） | 延迟计量单位，1 RT = 2 GT。默认中继器档位表示 1–4 RT。到期时间保持 GT 精度，允许触发和到期都位于奇数 GT。 |
| Immediate Update | 在触发写入或通知的当前执行链中进入指定通知阶段，可以在同一 GT 内执行。组件仍按自己的语义决定是否排队或修改状态。 |
| Scheduled Block Tick | 目标方块类型、位置、到期 GT、优先级、刻内插入顺序。记录入队、去重、收集、执行和跳过的理由。队列身份与 RustCraft 通用持久任务分开。 |
| Block Event | 持有目标方块类型、位置、事件 ID 和参数的独立队列。活塞检查可插入候选事件，由后续 Block Event 阶段检查当前类型、供电、活动区块和运动状态，再执行或跳过。 |
| 运动完成 | 活塞启动、移动占位及完成单独观察。运动完成、通知和渲染插值各自有阶段。 |

原版映射分别列出计划刻的到期时间、优先级及刻内序号，区分容器候选顺序与同刻排空顺序。实测的分块排序用例中，Chunk 内先按到期 GT 决定队首。两个 Chunk 的已到期队首按优先级和刻内序号选择执行。对同一类型和位置的重复请求保留第一次插入。方块计划刻与 Block Event 也有独立入口。同刻重入、区块失活后重试以及不同触发阶段的精确条件仍须以下游实验确认。[计划刻对照](java-redstone-verification.md#order-evidence) · [ScheduledTick](https://mappings.dev/1.20.1/net/minecraft/world/ticks/ScheduledTick.html) · [LevelTicks](https://mappings.dev/1.20.1/net/minecraft/world/ticks/LevelTicks.html)

RustCraft 的 `/tick` 控制 GT。F3+R 的 RT 单步在同一权威时钟上连续执行两个 GT，保留两个完整报告及中间状态，计划交互仅投入首个 GT。奇数 GT 恢复时仍执行完整窗口。实际 Java 1.20.1 命令表没有 `/tick`，RustCraft 继续把命令和 F3+R 作为调试控制面。[Java 1.20.3 命令发布记录](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-20-3)

参考预设的中继器在计划刻阶段更新。四档边沿的延迟为 2、4、6、8 GT。输入在升沿到期前撤去时，已安排的升沿仍可产生一段完整输出。侧向锁定会冻结输出，锁定与解锁按相邻二极管的输出方向判定。玩家放置回调在已有输入时安排 1 GT 的启动刻。输出变化向输出格及其指定邻居发 NC，邻侧收到形状更新的活塞仍可保留 BUD 状态。[中继器差分](java-redstone-verification.md#repeater-evidence)

观察者的观察面收到 Shape Update 后，以普通优先级安排 2 GT 后的升沿，再安排 2 GT 后的降沿。等待期间保留第一次安排的截止时间。输出背面发出强度 15 的普通与直接信号，观察者本身不传导外来电力。升沿写入引起的形状通知在该脉冲的降沿入队前处理，再向输出格和指定邻居发 NC。[观察者差分](java-redstone-verification.md#observer-evidence)

红石火把从附着面读取输入。输入变化可安排 2 GT 后检查，执行时复查支撑侧电力。亮着时，附着面之外的普通输出为 15，只有上方同时收到直接输出。60 GT 窗口内第八次熄灭会安排 160 GT 后复查，恢复时仍需失去输入。灭灯记录属于当前维度运行期，恢复刻随世界保存。[火把差分](java-redstone-verification.md#torch-evidence)

比较器将输出强度与方块状态分开保存。侧向取两个控制信号的较大值。比较模式在背面输入大于等于侧向时保留背面强度，减法模式取减去侧向后的非负值。邻居变化通常经 2 GT 计划刻更新，右键切换模式会立即重算。强度独自变化时，定向输出通知仍可更新红石粉。观察者会对比较器收到的形状变化作出响应。[比较器差分](java-redstone-verification.md#comparator-evidence)

拉杆可安装在地面、墙面或顶面。翻转立即改变输出，开启时向六面输出普通信号 15，向支撑面输出直接信号 15。右键同时向拉杆与支撑周边发送更新。命令写入开启状态只发出该写入本身的通知。移除支撑时拉杆脱落，并通知邻居重新读取输出。[拉杆差分](java-redstone-verification.md#lever-evidence)

石按钮和橡木按钮按下后立即向六面输出普通信号 15，并直接充能附着方块。松开分别在 20 GT 和 30 GT 到期，期间重复右键保留原期限。普通压力板在 20 GT 重新检测，轻重测重压力板在 10 GT 重新检测。当前运行时读取玩家和掉落物的包围盒，石压力板只接受其中的玩家，橡木和测重板也接受掉落物。投射物等其他实体触发仍待接入。[按钮和压力板差分](java-redstone-verification.md#controls-evidence)

发射器和投掷器收到有效的直供或准连接通知时设置触发态，动作延后 4 GT。撤电清除触发态，待办执行时检查对应类型。投掷器面对可接收容器时转移一件，目标满时保留物品。普通吐出路径产生带稳定身份的掉落物。库存变化向邻近比较器发送专用更新。宿主可通过权威库存事务设置九个槽位。玩家容器界面和发射器的特殊物品行为仍待接入。[发射器和投掷器差分](java-redstone-verification.md#ejector-evidence)

## 空间、供电和激活

空间查询沿 Chunk/Section 网格获取 `Loaded(state, revision)`、`Unavailable` 或 `OutOfBounds`。不可用的格子是否阻塞、延期或按边界默认值处理，由调用的版本规则决定。形状、碰撞、渲染遮挡、红石导电与推拉反应分别从状态及注册表属性派生。[RCF-033、074](rcf-decisions.md)

| 查询或状态 | 语义 |
|---|---|
| 空间邻接 | 几何偏移及六方向，跨 Chunk 与 Section 使用相同世界坐标。 |
| 信号连接 | 红石粉四个水平面的 `none`、`side`、`up`，考虑高低台阶、遮挡、方块导电性与端口方向。连接状态和输出资格分别求值。 |
| 发出信号 | `signal(source, toward, kind, context) -> 0..=15`，方向用从源到接收者定义。普通输出和直接输出均可查询。 |
| 传导与充能 | 对导电方块用输入侧与来源记录强弱充能。强充能可继续向符合规则的邻格供电，弱充能对尘线和部分设备的影响不同。数值聚合方式按查询决定。 |
| 组件激活 | `activation(device, snapshot)` 返回直接输入、QC 输入、侧面输入、锁定或无输入，带上产生结论的坐标和方向。 |
| 实际状态 | 注册的 BlockState 和必要的方块实体状态，例如门限输出、待执行动作、运动进度。由合法事件经过权威提交更新。 |

红石粉从六面读取外部电力，以单独的查询上下文排除尘线参与外部供电，再考虑相邻尘线的衰减。上下文随调用传递，缓存键包含它。原版差分已覆盖垂直电源、强充能支撑和导体隔开的粉末。查询本身只读。信号值、充能状态、激活条件、通知到达、动作入队和动作完成分别记录。电力拓扑可用于候选查询，更新接收集合由事件语义确定。[供电差分](java-redstone-verification.md#power-evidence) · [外部电源差分](java-redstone-verification.md#wire-external-evidence)

参考预设的粉末方块状态记录四个水平连接及电平。物品放置以十字为初始形态，原版默认的直接写入状态对应 `rustcraft_java:wire_0_0`，孤立粉末允许通过右键切换。渲染使用已提交的形态。轨迹应分别记录连接和实际电平，例如隔着玻璃台阶，低处的可见 `up` 连接仍存在，高处源却不会使低处获得电平。[连接差分](java-redstone-verification.md#wire-shape-evidence)

## 通知和调度

每次权威写入保留来源、修改原因、更新标志、前后状态和事件 ID。写入可触发以下不同类别。相同的空间范围内可能出现多次合法通知。

| 类别 | 作用与执行入口 | 精确顺序待验项 |
|---|---|---|
| Neighbor Changed（NC） | 将指定源的变化通知给规则选中的邻格。组件可据此查询激活条件，安排重查或动作。 | 六方向顺序，排除面，多目标通知被递归更新打断或恢复的顺序。 |
| Shape Update | 给相应面重算邻接形状、支撑和连接。可生成状态替换及随后通知。 | 方块放置和拆除的标志组合，形状支撑丢失与 NC 的先后。 |
| Comparator Update | 按水平方向通知相邻比较器，或穿过一个导体通知第二格的比较器。普通编辑继续派发其自身的通知。 | 容器状态、展示框及其他模拟输出源的完整通知条件。 |
| Scheduled Block Tick | 消费一个有序的到期记录，检查目标方块类型，执行组件定时入口。 | 优先级、局部队列和同刻批次，失活区块与恢复后的相对顺序。 |
| Block Event | 执行特定方块安排的动作，记录取消、实际写入以及子事件。 | 重复身份、阶段内新事件、无效或失活目标的处理。 |
| Commit / Publish | 原子提交验证过的写入，更新 revision 并发布协议、存档和渲染的变化。 | 玩家与动作冲突按版本化顺序裁决。派生缓存失效不进入通知队列。 |

执行器按对应阶段收集并消费队列。队列记录来源、目标、方向、父事件及有序位置。参考实现首先落实有证据的通知范围和顺序，包括同位事件的重复条件。不得按位置统一排序、模拟每 GT 轮询或按拓扑广播。需要阈值的地方复用服务端权威预算配置的承载能力，但游戏可见的深度、跳过和报错路径由规则决定。原型的 `WORK_LIMIT = 4096` 只代表现行限制。原版收集式邻居更新器具有独立的层栈和链上计数。[CollectingNeighborUpdater](https://mappings.dev/1.20.1/net/minecraft/world/level/redstone/CollectingNeighborUpdater.html)

粉末电平变化经过形状通知，再从该格及六个相邻格派发邻居通知。七个中心按固定到 Java 17 的散列桶序遍历，同桶保留插入顺序。粉末移除会从六个相邻格派发邻居通知，在所测装置中先于移除引起的形状通知。[粉末通知差分](java-redstone-verification.md#wire-notice-evidence)

## QC、BUD 与动作生命周期

活塞、粘性活塞、发射器和投掷器用组件专属的查询。普通活塞的六向探针覆盖直接供电和组件上一格的准连接输入。相邻活塞面排除在直接检查之外，准连接位置仍按上方参考格取样。查询额外区分区块数据缺失。位置只是供电查询参数，改变准连接来源的方块仅发出自己的合法通知。新预设由放置或有效 NC 检查动作，并在运行 Block Event 时复查供电和目标。Shape Update 单独处理支撑。容器类方向与动作另行验证。[1.20.1 活塞检查、供电查询和动作入口](https://mappings.dev/1.20.1/net/minecraft/world/level/block/piston/PistonBaseBlock.html)

只读诊断覆盖普通活塞、粘性活塞、发射器和投掷器。报告包含方块状态、朝向、直供或准连接来源、最近的有效检查、排队结果、运动和阻挡位置。只有一次运行中对同一对象捕获到从状态一致到可动作失配的转换，并确认两次观察之间没有有效检查，才报告疑似缺少通知。对象更换、区块失活、重开或证据超出保留窗口后，失配按历史不足或视图不可用报告。诊断不会写入方块、补发通知、修改任务或新增持久化标志。[诊断与导出](java-redstone-verification.md#bud-inspection)

保存的实际状态与方块实体通过版本化 schema 恢复。通用 RustCraft 任务继续按原有合同持久化。Java 兼容的方块计划刻、Block Event 和移动状态分别核对存档、区块卸载和重载生命周期。保存、重载和渲染重建均不得以全区扫描重算 BUD。事件历史不足时明确报告，参考 [BUD-012 重开差分](java-redstone-verification.md#qc-restart-evidence)。

V3 检查点不保存未执行的活塞 Block Event，保存操作本身保留运行中的事件队列。活塞运动保存上一 GT 的进度，恢复后首个活动 GT 等待方块实体就绪，随后继续运动。方块计划刻仍保存截止 GT 和可观察相对次序。V2 保留原有事件与运动恢复语义。此次规则升级影响权威检查点、运动推进、只读诊断及启动预设，不改变记录 Schema；版本身份决定字段语义。决策依据为用户要求的 Java 1.20.1 生命周期兼容和独立进程原版实验。

实现依赖为 **参考采样与最小类型化事件 → 方向性供电和分发 → 计划刻与 Block Event → P0 实现及 QC/BUD → P1 → P2 → 并行和缓存门禁**。同一阶段先建立最小原版差分再扩展装置。版本化测试覆盖、可回放检查点和性能样本分别归档。[RCF-006、035、036、041、069–074](rcf-decisions.md)

并行的可用边界是从封存视图计算候选查询或布局计划。结果带上规则身份、输入修订、读范围、预期阶段和排队序号。提交之前验证依赖和事件顺序，失效结果在权威视图重算。PRNG 消费仍在版本化顺序内。正式启用前，用同样的输入与检查点比较参考顺序、缓存开关、不同线程数和乱序完成，并核对动作、通知、因果以及中间状态等价。
