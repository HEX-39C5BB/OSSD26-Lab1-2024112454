## 4. 确定性核心：时间、事件、事务与随机数

<a name="section-4-1"></a>

### 4.1 Tick 时序契约

- **Simulation Clock** 采用 50 ms 固定逻辑步长（20 Hz）。World/Dimension Time 各自持有可暂停、改变速度或冻结的世界时间表示，昼夜快进独立于模拟 Tick（RCF-006/046、TBD-017）。
- 系统通过声明式执行阶段和读写依赖构建有向无环调度图，MVP 顺序执行；并行化必须维持既有可观察语义（RCF-035）。
- 原生 Tick 调度 `rustcraft:tick_schedule` 版本 1 的阶段顺序为事务提交 → 玩家模拟 → 区块视距更新 → 快照发布。启动时按预设构建调度，并校验阶段依赖和读写冲突。调度身份随检查点保存。
- 方块更新、红石和版本化特殊调度不被自动并入普通 ECS System；它们按 RCF-023/024 的显式队列规则运行。
- 玩家命令、服务器管理操作和模组事件必须具有合法 Session/Capability 和确定性提交时点。

<a name="section-4-2"></a>

### 4.2 单次修改的逻辑过程

1. 接受类型化 Mutation Request，绑定来源身份、有效规则 Manifest、操作序号及预期对象范围。
2. 验证权限、前置条件、读写集合与现有状态版本；根据契约调用 Pre Hook。
3. 依据执行阶段、依赖与稳定排序处理同 Tick 冲突；按规则拒绝、受控重试或可证明安全的合并。
4. 在声明的原子范围内提交权威世界状态；失败不得对外发布部分提交。
5. 更新对象版本、发布已提交变化摘要（RCF-069），再发布有效只读快照（RCF-070）。
6. 存储、光照、网格、复制、导航等消费者根据版本和依赖各自处理；成功提交内存不等于 RCF-067 已落盘。
7. 将必要的结果、观察通知和客户端增量输出，避免重复触发游戏规则事件。

**技术难点：** 原版部分行为允许特定顺序下的中间状态被观察。事务边界必须按版本化规则声明，不能将整个 Tick 强行变为单一不可观察事务。

<a name="section-4-3"></a>

### 4.3 Read View 与异步任务

Read View 明确对象集合、生成时点、版本、依赖边界、权限与生命周期。Section 使用 Uniform/Paletted 数据快照，实体组件可按需复制或共享不可变数据。后台结果附带源对象/依赖版本，过期时丢弃或重算。快照引用受到 Ticket、内存与时间预算控制；不实现 MVP 全局 MVCC。

<a name="section-4-4"></a>

### 4.4 随机数的跨规则语义

PRNG 算法、世界/维度/区块/系统种子派生、随机流身份/共享关系、调用消耗顺序与持久化单独版本化（RCF-072）。原生规则默认可以分域独立随机流；原版兼容实现允许复现共享流及其副作用。异步任务完成顺序不能成为随机流消耗顺序。失败事务/重试是否消耗随机状态必须由操作契约声明。认证等安全随机来源独立于游戏 PRNG。

P3 的 `rustcraft:seed_derivation@1` 从持久化的 `u64` 根种子派生世界种子，再按维度实例的稳定标识派生维度种子，按有符号区块坐标 `(x, z)` 派生区块种子。系统使用稳定的命名空间标识，在世界、维度或区块范围内独立派生。通过 `Server::world_seeds()` 获取 `WorldSeeds`，用 `for_scope` 或 `for_system` 派生。相同输入的结果与调用顺序及进程重启无关。

版本 1 依次编码父种子、单字节域标记及该域参数。世界、维度、区块和系统的标记分别为 1、2、3、4。整数固定为 8 字节小端序，标识为字节长度加 UTF-8 原文，区块参数按 `x`、`z` 编码。字节串使用 FNV-1a 64 位折叠，再用 SplitMix64 混合步骤产出种子。固定向量覆盖负坐标、标识编码和系统域。平坦生成器版本 1 继续使用自己的根种子与绝对方块坐标公式。参见 [实现与固定向量](../crates/authority/src/seed.rs)。

`rustcraft:random_stream@1` 以派生出的系统种子初始化 SplitMix64。受信权威系统通过 `Server::system_random` 暂存随机取样，用 `next_u64` 取值，显式调用 `commit` 推进保存状态。放弃取样后可从相同位置重试。种子相同的不同作用域和系统分别记录进度，实际身份使用标识与坐标。每个世界支持 256 条已提交的流，每个维度或系统标识为 1–128 字节。存档记录已提交的 64 位状态。参见 [随机流实现](../crates/authority/src/random.rs)和[持久化](persistence.md#section-13-5)。

<a name="section-4-5"></a>

### 4.5 延迟任务

RCF-073 任务存储类型、稳定目标标识、时间域、到期规则、稳定排序、取消/重复处理策略、生命周期绑定与必要持久化。实体销毁、区块卸载、维度休眠和世界重启必须各自有定义的保留/取消/恢复语义。JS 内存闭包不自动属于可持久化 Scheduled Operation。

P3 首版提供世界级到期事件。受信权威系统调用 `Server::schedule_task(delay_ticks)`，返回任务编号和到期 Tick。延迟至少为一个 Tick，每世界最多排队 4096 项。`Server::cancel_task` 按原任务句柄取消待处理项。提交阶段处理完会话请求后，按到期 Tick、任务编号依次出队，通过 `TickReport::due_tasks` 发布。每项在该世界时间线只出队一次。检查点保留待处理项与下一编号，恢复后继续按原到期 Tick 处理。参见 [延迟任务回归测试](../crates/persistence/tests/scheduled_tasks.rs)。

受信权威系统可用 `Server::schedule_operation` 排队两种操作。定时替换方块在到期时比较当前方块与预期方块，匹配后走现有的权威方块编辑与玩家碰撞检查。定时停用区块在到期时检查玩家占用，并交给相同的区块管理路径。视距流送仍可以重新激活所需区块。失败的任务记录拒绝原因，重试由调用方重新排队。

本地 `TickReport::task_events` 记录排队、取消和到期结果。服务端按 Tick 输出 `task_queued`、`task_canceled`、`task_due` 或 `task_rejected`，带任务编号、到期 Tick 和操作类型。诊断随下一次 Tick 发布，持久化记录只保存待处理操作与编号。

在仓库根目录运行本地演示，确认两种操作成功、预期方块不符和占用区块两类拒绝均出现在日志中，最后输出 `event=task_demo_complete`。

```sh
cargo run --locked -p rustcraft-host --no-default-features --bin rustcraft-server -- --task-demo
```

检查已有存档时，使用 `--list-tasks WORLD`。命令只读 `CURRENT` 指向的检查点，输出代号、当前 Tick、待处理数量，以及按到期 Tick 和任务编号排序的条目。每项包含剩余 Tick、操作类型和目标参数。

```sh
cargo run --locked -p rustcraft-host --no-default-features --bin rustcraft-server -- --list-tasks ./world
```

关闭世界后，可对已有检查点排队或取消任务。延迟是相对当前保存 Tick 的正整数，方块使用注册名，区块参数使用区块坐标。每次成功编辑使用当前代作为写入租约，发布新代并保留原代。命令打印新代号、任务编号和到期 Tick，世界从同一 Tick 恢复。无效参数、未知任务或代号已变化时返回错误。

```sh
target/release/rustcraft-server --schedule-replace-block ./world 20 2 0 2 rustcraft:empty rustcraft_content:basalt
target/release/rustcraft-server --schedule-deactivate-chunk ./world 40 -1 0
target/release/rustcraft-server --list-tasks ./world
target/release/rustcraft-server --cancel-task ./world 2
```

将示例中的 `2` 换成清单显示的实际任务编号。用 `--open-world ./world` 恢复执行。自动验收从相同检查点对比连续执行和关闭后重开的最终世界状态，覆盖替换冲突、成功停用和取消。参见 [命令行重放测试](../crates/host/tests/task_commands.rs)。

## 5. 版本化规则系统与严格预设

<a name="section-5-1"></a>

### 5.1 四类对象

- **Mod：** 声明功能与依赖的内容/规则提供者，初期为静态 Rust 内建。
- **Capability：** 诸如 Block Update Semantics、Combat Evaluation、World Generator、Recipe Matching 等明确的语义能力。
- **Implementation：** 具有稳定身份、版本、支持区间和优先级约束的能力实现。
- **Preset：** 选择一组能共同构成合法世界行为的规则组合，如 RustCraft Native、Java 版本、Bedrock 版本、Strict Ruleset、自定义混搭。

解析器输入含版本预设、用户/整合包/世界配置、模组依赖、权限要求及互斥限制；输出**Resolved Runtime Manifest/Lockfile**，明确实现选择、精确版本、来源/哈希、规则配置、合法的覆盖关系。无法解析时应诊断并拒绝不安全启动，而非静默退回默认实现。

<a name="section-5-2"></a>

### 5.2 原版兼容的行为颗粒度

规则语义至少可按世界生成、红石/方块通知、实体 AI、战斗/击退、物理、随机数、战利品、伤害、交互、容器点击、配方、音画表现和脚本 API 分离。不同领域可以组合，但跨域调用必须满足依赖约束。例如 Java 某版本红石规则不能在没有匹配调度语义的情况下套用不兼容的更新队列。

原生预设 `rustcraft:native` 版本 1 绑定 `rustcraft:flat`、`rustcraft:tick_schedule`、`rustcraft:player_movement`、`rustcraft:block_inventory`、`rustcraft:seed_derivation` 和 `rustcraft:random_stream` 各自的版本 1。检查点加载先解析固定组合，再创建世界。以后修改已锁定语义时，应提供新版本，并保留旧版本供已有世界继续运行。

<a name="section-5-3"></a>

### 5.3 技术生存特性与 Strict Ruleset

- **原版兼容 Preset：** 若目标版本存在更新抑制、TNT 复制、地毯/线/沙复制等可观察行为，应分别建模、标明证据和通过差分测试确认；不能断言它们都依赖同一种底层漏洞。
- **Strict Ruleset：** 定义独立、明确、可检验的不变量，如物品守恒事务、非法状态拒绝、操作生命周期一致性、权限边界和可解释的规则结果；不等于把 `exploit=false` 开关一次全关，也不承诺绝对零漏洞。
- **混搭 Preset：** 只有依赖解析和验证矩阵允许的组合才能对外标注兼容；不要求穷举全部排列。

<a name="section-5-4"></a>

### 5.4 兼容性证明层级

1. **Designed：** 接口和规格明确，尚未实现。
2. **Implemented：** 可执行功能存在，不保证原版行为一致。
3. **Tested：** 已通过指定的测试集和目标环境。
4. **Verified-Compatible：** 有来源、黑盒基准、可复现差分结果和明确覆盖范围。

以上层级要出现在版本发布说明和模组兼容表中。单一 API 名称相同不等于行为兼容。

## 6. 世界、维度、数据模型及空间

<a name="section-6-1"></a>

### 6.1 世界容器结构

Server Host 管理多个潜在独立 World Instance；每个 World Instance 拥有一个 World Container；World Container 管理一个或多个 Dimension Instance。维度类型由模组注册，每个维度实例独立持有坐标空间、区块、实体、环境、时间及相关规则。MVP 只有一个 Host、一个 World Instance、一个 Dimension Instance。

<a name="section-6-2"></a>

### 6.2 空间数据分层

- **整数网格坐标**使用 `i64` 表示方块坐标，Chunk 和 Section 寻址从整数格网派生（TBD-008）。
- **实体连续位置**采用 `f64` 表示玩家和实体位置，存档按独立 Schema 编码（[§13.1](persistence.md#section-13-1)）。
- **渲染坐标**以相机为原点计算局部位置，降低大世界坐标的 GPU 精度损失。
- **维度关系映射：** 显式空间变换、视图映射与可穿越权限，不能滥用普通相机坐标变换作为游戏权威传送语义。

<a name="section-6-3"></a>

### 6.3 方块数据

Section 采用固定的 `16×16×16` 方块网格，Chunk 按纵向 Section 组织。平坦维度默认 `-64 ≤ y < 256`。创建世界时可配置垂直范围，随后写入存档并在加载时恢复。内存中的 MVP 表示为 Uniform 或 Palette + Bit-Packed，磁盘布局由独立存档 Schema 定义（TBD-009、[§13](persistence.md#section-13)）。

Block Type / BlockState Schema 启动时解析并冻结。运行时 ID 用于当前进程，存档使用稳定命名空间标识及版本化属性和映射。光照、群系、方块实体和扩展数据独立维护，普通方块由 Chunk/Section 管理。Dense 可作为后续内存优化。

<a name="section-6-4"></a>

### 6.4 实体与 ECS

采用独立 `bevy_ecs`，每个 Dimension Instance 拥有独立 ECS World。组件按访问模式使用 Archetype Table 或 SparseSet。RustCraft 管理确定性阶段、读写冲突解析和权威提交，初期顺序执行，后续启用并行前验证可观察语义（TBD-005）。

Entity Type、持久实例身份、运行时 ECS 句柄与版本化 Component Schema 分离。持久化通过独立 Schema，由 RustCraft Entity/Component API 提供模组扩展接口。实体在维度内创建、激活、休眠、卸载、恢复和销毁，跨维度迁移保持必要的稳定身份与一致性。结构性变更通过 Command Buffer 或受控事务提交。

<a name="section-6-5"></a>

### 6.5 空间索引与导航

方块直接通过 Chunk/Section 寻址；动态实体按对象类型采用简单分桶或后续动态 AABB Tree/BVH。Spatial Query 仅筛选候选，版本化物理/战斗规则负责精确结果。导航把 Navigation Profile、可遍历区域与代价、异步路径规划、路径验证及 Path Following 分开；MVP 不需要完整导航算法或生物 AI。

<a name="section-6-6"></a>

### 6.6 区块与缓存

Chunk 生命周期区分磁盘存储、加载、生成、权威模拟激活、客户端渲染可用和卸载。玩家、实体、任务、模组及远端视觉可申请不同能力 Ticket；渲染可见不自动激活红石/AI Tick。缓存按服务器世界数据和客户端 Mesh/GPU 资源独立预算，受 Ticket、引用、脏写回和版本依赖制约。MVP 简单加载/卸载、基本 Ticket、区块缓存与异步网格；长距离预读和跨维度负载预算后置。

首版本地客户端以玩家所在区块为中心，按方形范围更新活动区块。权威 Tick 在玩家模拟后、快照发布前提交视距更新，每 Tick 最多激活两个新增区块，优先处理近处区块。离开视距的区块停止活动并保留在驻留数据中，方块修改继续随检查点保存。客户端每帧最多重建四个区块网格，并按当前区块和相邻区块版本排除旧网格。

视距支持半径 1–16 的每个整数。半径 16 覆盖以玩家为中心的 33×33 区块，渲染远裁剪面为 512 格。预算内加载时，初始视野和跨区块后的新增区域逐步补齐。

## 7. 世界生成、群系、结构、刷怪和掉落

<a name="section-7-1"></a>

### 7.1 双层世界生成

底层 World Generator API 可整体替换；上层可选模块化生成阶段管线。世界种子、生成器版本、配置及必要随机状态共同决定可复现输出。区块异步生成不得因任务结束顺序改变结果；旧新区块相邻边界及生成器升级需有明确兼容策略。已生成旧区块的 retro-generation 只在显式允许和安全校验下执行。

P2 默认原生世界采用平坦分层地形，并用作回归场景。地衣岩、壤土与玄武岩组成首批原创方块，固定种子复现地下玄武岩分布。P2 内容优先补齐方块、库存反馈和基础音效（TBD-018）。

<a name="section-7-2"></a>

### 7.2 群系和环境

Biome Registry/Definition、分布策略、独立群系数据层、环境/生物生成规则及客户端颜色/天空雾表现分离。群系采样分辨率不必等于方块网格，不同维度可拥有各自环境及天气规则。MVP 少量群系和简单取样；动态生态与复杂气候算法后置。

<a name="section-7-3"></a>

### 7.3 结构与地物

Feature/Structure Registry、位置选择、布局规划、模板/处理器、跨区块协调及受控放置分层。结构放置要具备幂等性、冲突处理、旧区块边界约束以及稳定随机派生。地物和结构内容中的生物/战利品规则保持独立。MVP 仅简单树木/矿脉等基础地物及边界协调。

<a name="section-7-4"></a>

### 7.4 实体生成、人口上限和掉落

实体生成注册、候选采样、条件验证、确定性调度、种群统计、实体创建及自然消失分别版本化。区块已加载不自动拥有自然刷怪资格。Loot Registry、条件、池、函数、随机数消耗及结果提交分离；掉落生成不是物品已存在于世界，必须经过权威提交。MVP 不实现完整自然刷怪，仅允许基础实体创建和简单方块掉落。

## 8. 多维度关系与特殊空间场景

<a name="section-8-1"></a>

### 8.1 Dimension Relationship Graph

维度关系图描述**游戏世界之间的空间和语义关系**，绝不能与 GPU 的 Render Graph 混同。关系类型可组合但互不隐含：物品传输、实体传送、远端可视投影、投射物穿越、远端命中、声音传播、可选物理连续连接。每条关系有来源/目标 Dimension Instance、空间映射、方向、权限、资源预算及版本化规则。

<a name="section-8-2"></a>

### 8.2 关键验证场景：倒悬天空维度与末影珍珠

1. 维度 A 的天空区域建立到维度 B 的倒悬远端视觉投影；相机获得 B 的受限 View Context，视图加载 Ticket 不默认激活 B 的全部模拟。
2. 维度关系独立声明是否允许投射物与远端场景交互；如果只有可视关系，末影珍珠不能自动穿越。
3. 当显式允许合法的 Projectile/Impact/Entity Transfer 路径时，末影珍珠在 A 发射、按版本化弹道执行，并按照空间映射处理对应边界/命中。
4. 命中规则验证来源玩家身份、目标维度和安全重定位；跨维度实体迁移使用受控协议，失败不能导致玩家重复或丢失。
5. 客户端重建视图、插值与相机状态，处理不连续位置迁移；音画效果独立于物理合法性。

**当前状态：** 该场景是长期验收用例，不是 MVP；任何架构优化不得使其在理论上无法实现。

<a name="section-8-3"></a>

### 8.3 循环视图与预算

后续多视图系统为每个视图声明关联世界、投影链、递归深度、像素预算、显存预算、对象权限和依赖版本。循环投影必须有终止与降级策略。远端视图可以读取快照和复用纹理，但不自动创建物理世界连接。

<a name="section-10"></a>

## 10. 玩家、实体行为与交互子系统

<a name="section-10-1"></a>

### 10.1 玩家身份、会话与游戏模式

Player ID 稳定、外部认证身份与凭据独立、Session 是临时在线状态、Player Entity 可以创建/销毁/重建。显示名称和 ECS 句柄都不是可靠的持久 Player ID；外部 Microsoft 身份绑定后续通过标准认证接入，不采集密码明文。Game Mode 注册与能力解析分离，创造模式飞行等游戏内能力不等于管理员授权。MVP 只有本地玩家身份、基础模式、玩家状态保存和会话恢复。

<a name="section-10-2"></a>

### 10.2 动作与交互

`rustcraft:player_movement` 版本 1 固定现有权威移动语义。每 Tick 的水平移动上限为 0.24 格，飞行升降为 0.30 格。普通跳跃将竖直速度设为 0.40 格/Tick，同一 Tick 开始应用重力。重力每 Tick 将竖直速度降低 0.06 格/Tick，最大下落速度为 0.90 格/Tick。移动按 X、Z、Y 逐轴碰撞，未加载区块构成边界。双击飞行、取消飞行和下降触地沿用 [§9.7](client.md#section-9-7) 的行为。输入、模拟和保存的运动状态均由预设选定版本处理。

玩家破坏、放置、使用方块/物品、实体交互按「请求 → 权威目标/距离/模式验证 → 版本化动作规则 → Hook → 受控提交 → 同步」处理。多 Tick 挖掘必须建模开始、持续、取消和完成，客户端动画可预测但不能宣布实际成功。方块更新、红石依其自身版本化规则排队。

`rustcraft:block_inventory` 版本 1 锁定了现有的 5 格方块射线及玩家放置、破坏规则。权威快照与操作提交使用同版目标判定。破坏校验命中区块版本，放置还校验相邻区块版本和玩家碰撞体。

<a name="section-10-3"></a>

### 10.3 物品、容器与配方

ItemStack 包含稳定物品定义引用、数量和版本化数据组件；槽位与受控插入/提取接口支持复合原子事务。容器实例独立于 GUI，容器交互 Session 绑定合法玩家、容器和版本；断线、距离变化、容器销毁或跨维度迁移需要使旧操作失效。配方注册、原料 Predicate、匹配、候选优先级、加工状态、产物/剩余物与提交分离。客户端配方预览不能代替实际执行时的重新验证。

`rustcraft:block_inventory` 版本 1 保留 P2 的有限堆叠规则。放置从选中槽扣除一件，破坏将对应方块放回库存，由同一权威事务提交方块与库存变更。库存空间不足时拒绝回收操作。当前本地玩家库存有 8 个槽位，支持选择和转移，同类方块每槽最多 64 件。槽位操作校验库存版本。先在临时库存上执行扣减或回收，方块编辑成功后才发布库存与音效。

<a name="section-10-4"></a>

### 10.4 实体属性、AI、战斗和导航

- 属性、修饰符来源、计算顺序、状态效果生命周期及周期触发独立版本化；装备变化必须正确撤销稳定来源修饰符。
- AI 定义感知、记忆、导航、行为意图与调度，不直接写入物理状态；Goal-Based/行为树/效用/状态机均为可替换实现。
- 战斗分离命令、命中/冷却、伤害上下文、减免、击退、死亡、掉落及状态效果；权威提交保持一致。
- 导航数据、可通行性和路径规划不决定最终物理运动；MVP AI/自然刷怪完整实现后置。

<a name="section-10-5"></a>

### 10.5 游戏模式、饥饿与死亡

玩家生存状态（饥饿、饱和度、消耗、经验、等级）与通用属性不同；消耗、食物、恢复和死亡数值结算独立版本化。死亡状态机、重生点 Provider、位置验证、玩家实体重建及 Session 重关联需要协调事务，防止重复掉落和孤立实体；稳定 Player ID 不变。MVP 主要为创造模式风格，不要求生存、死亡惩罚或床/重生锚。

<a name="section-10-6"></a>

### 10.6 装备、附魔、药剂、投射物、爆炸和火焰

- **装备/耐久：** 装备槽合法性、实例耐久、损耗触发、损坏/修复与属性撤销分离。
- **附魔：** Enchantment Registry、物品附魔组件、适用性/互斥、来源/随机获取、效果触发分别版本化；复用现有战斗/掉落/耐久系统。
- **药剂：** 药剂内容、酿造配方、饮用/喷溅/滞留/药箭投递及状态效果执行独立；不用通用工业流体模型。
- **投射物：** 实体生命周期、发射者身份、版本化弹道、命中排序、命中效果和状态同步分离。跨维度穿越/命中/玩家传送由显式关系授权。
- **爆炸：** 来源、传播、方块影响、实体曝光/击退、连锁反应、战利品与表现分开；历史 TNT 特性分项测试，严格模式不简单用一个开关概括。
- **火焰：** 点燃来源、方块可燃性、火焰传播、实体着火、环境熄灭和客户端表现分开；不是热力学模拟。

以上子系统均已确认架构边界；除最小可玩目标所需接口外，完整玩法后置，防止在 MVP 期间实施所有后期系统。
